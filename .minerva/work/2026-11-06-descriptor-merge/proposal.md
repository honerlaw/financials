# Proposal: descriptor-merge

**Date**: 2026-11-06
**Status**: Shipped

## Goal
A recurring bill whose Plaid merchant name changes mid-history is detected as one stream. Before stream detection, merchant groups that share a dominant normalized transaction name (Plaid's `name`, stored as `transactions.description` — for card issuers like AmEx this is the card-network descriptor and stays stable when Plaid's `merchant_name` enrichment changes) are merged, on both the indexed and the in-memory grouping paths, but only when the merge is unambiguous and looks like a rename: never across two different Plaid merchant entity ids (knowledge 032), never across opposite sides (charges vs deposits), never when the groups' date ranges overlap.

## Why
The user asked why a long-running monthly charge on their card — the same descriptor on every charge — is not counted on /recurring. Plaid's merchant_name for it recently changed to an unrelated name; grouping keys on merchant_name (or entity id), so the history split into an old-name group whose last charge is more than 1.5 cadences old (→ inactive, not counted) and a new-name group with too few charges to be a stream (< MIN_OCCURRENCES). Replayed as one group it is an active monthly bill missing from the recurring total. The user chose "also match on the raw card descriptor", keeping the rule that two different Plaid merchant ids never merge. A local simulation over the production transactions (name keys only — entity ids are not visible over HTTP) found only a small number of descriptors shared between groups, every pair the same merchant under two Plaid names; a handful of groups change status — renamed bills become active streams, and a few one-off purchases a year apart become annual streams (listed, never counted). Production data informed this design but no production names, amounts or counts are recorded here.

Entity ids of the real case are unknown. The old name is a truncated descriptor (what Plaid emits without a merchant match) and the new one a proper business name (typical of an entity match), so the likely shape is "one side has an entity id, the other none" — which merges. If both halves carry different entity ids, the 032 rule the user asked to keep blocks the merge; the post-deploy check reports that outcome rather than overriding the rule.

## Approach
- New pure function `merge_by_descriptor(groups)` in `app/subscriptions.py`; it materializes the iterable, never mutates the input lists, and returns a new list of row lists (same shape).
- **Dominant descriptor** of a group = the most common non-empty `normalize_merchant(t.description)` over its rows, ties → lexicographically smallest; `normalize_merchant` is computed once per distinct description string (memoized per call), not per row. Descriptors shorter than 5 characters never merge (mirrors `_similar`'s 5-char prefix guard). This reuses `normalize_merchant`; no new key derivation (issue #46 unaffected).
- **Buckets**: groups bucketed by dominant descriptor. A bucket whose groups carry **two or more distinct `merchant_entity_id`s** is ambiguous and merges nothing. Otherwise, groups are split by **side** (signed median amount < 0 → inflow, else outflow; the same test `_build_stream` uses). Each side is sorted by a total order — (earliest date, latest date, display name, row count, sorted descriptions, sorted amounts, sorted entity ids) — and merges into one group **only if every pair of its groups is date-disjoint** (each next group starts strictly after the previous one ends; a shared day counts as overlap). If any two overlap, nothing on that side merges. (The drafted greedy accumulation was dropped in review: it let two short groups nested inside a concurrent longer group merge with each other.)
- Called once per request: at the top of `detect_subscriptions_from_groups` and `bills.detect_recurring_from_groups` (`detect_bills_from_groups` delegates to the latter, so it is not merged twice). `detect_subscriptions`/`detect_bills` route through these, so the indexed and in-memory paths both see merged groups.
- Exact equality only: a comment pins that fuzzy descriptor matching here would reintroduce the per-request quadratic cost knowledge 029 removed. Cost is one pass plus a per-bucket sort — O(n log n), small.
- The persisted index (`merchant_groups` / `merchant_group_keys`) keeps representing the pre-merge grouping; no schema, index, `GROUPING_ALGO_VERSION` or `grouping_key` change. The module docstring says so.
- A merged stream's name is `_display_name`'s most common merchant_name (unchanged behaviour), so a renamed bill keeps its longer-lived name.
- **Deliberately conservative.** The non-overlap rule is strict: if a transition month carries charges under both names, or Plaid re-enriches only some old rows, the ranges interleave and the groups stay split — today's behaviour, never a false merge. A third group with a different entity id sharing the descriptor likewise blocks the bucket. `original_description` is not used: it is not in `_DETECTION_COLUMNS` and is empty for many rows. For an issuer whose `description` simply equals the enriched `merchant_name`, the merge is a no-op.
- Out of scope: a manual merge/unmerge override or descriptor deny-list; fuzzy descriptor matching; the annual bucket.

## Success criteria
1. Unit tests for `merge_by_descriptor`: the renamed-merchant case (an inactive monthly history plus two fresh charges under a new name, same descriptor) becomes one active monthly stream; different descriptors stay separate; two groups with different entity ids never merge, and a bucket holding two entity ids merges nothing (including a no-entity third group); an entity group and a no-entity group with the same descriptor merge; overlapping date ranges do not merge; three sequential groups chain into one; an outflow group and an inflow group with the same descriptor do not merge; descriptors under 5 characters never merge; inputs are not mutated; the output is identical under every permutation of the input groups.
2. Route test: /recurring shows the renamed-merchant bill once — one row, its name, its monthly figure — and the expense headline includes it.
3. A renamed-merchant corpus is added to the indexed-vs-in-memory parity tests in `tests/test_merchant_groups.py` and passes; the /recurring query-count test passes; `uv run pytest` passes.
4. After deploy, production /recurring either lists the renamed bill as one counted monthly expense, or the reason it did not merge (two different Plaid merchant ids, or overlapping date ranges) is identified and reported to the user (checked by reading the page; nothing real committed).

## Open Questions
- One-off purchases a year apart under a shared descriptor can become annual streams (listed under Annual, never counted) — accepted noise; the date-disjointness guard does not exclude them.
